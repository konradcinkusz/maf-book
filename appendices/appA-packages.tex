\chapter{Package and Version Reference}
\label{app:packages}

Agent Framework publishes roughly three dozen NuGet packages under the
\code{MicrosoftAgentFramework} account. This appendix lists them, grouped the way
they actually ship.

\begin{versionbox}
Every version in this appendix was read from \code{nuget.org} in \mafdate{}.
Treat it as a dated snapshot. Before starting new work, check
\code{nuget.org/profiles/MicrosoftAgentFramework} and
\code{github.com/microsoft/agent-framework/releases}.
\end{versionbox}

\section{One line, four maturities}
\label{sec:trains}
\index{release trains}
\index{packages!maturity suffixes}
\index{packages!one release line}

Earlier in the framework's life the family moved in \emph{trains} --- separate
groups of packages, each on its own version line and publication schedule. That
is no longer true, and the change is recent enough that most written advice about
it, including earlier drafts of this book, is out of date.

Since \code{1.11.1} in late June 2026 the family publishes as \textbf{one line}:
every package shares a base version and a publication date, and differs only in
its prerelease suffix. At \mafcore{}, published \mafdateexact{}, there are four
maturity tiers.

\begin{center}
\small
\begin{tabularx}{\linewidth}{@{}lX@{}}
\toprule
\textbf{Suffix} & \textbf{Packages} \\
\midrule
none --- stable & Core, Abstractions, OpenAI, Workflows, Workflows.Generators,
Workflows.Declarative, GitHub Copilot, and \textbf{the Harness} \\[4pt]
\code{-rc1} & Purview, and declarative \emph{agents} \\[4pt]
\code{-preview} & Hosting and its ASP.NET Core, A2A and Azure Functions
companions; Foundry client and hosting; A2A; DevUI; Cosmos NoSQL; Hyperlight;
Tools.Shell; Copilot Studio; Anthropic; DurableTask; LocalCodeAct \\[4pt]
\code{-alpha} & Hosting.OpenAI, Valkey, Mcp \\
\bottomrule
\end{tabularx}
\end{center}

Three consequences, and they are not the ones that applied a year ago.

\textbf{The harness is stable now.} It joined the main line at \code{1.14.0} and
shipped without a prerelease suffix. If you avoided it because it was preview,
that reason has expired --- though Chapter~\ref{ch:harness} has a different
reason to be careful with it.

\textbf{A single MSBuild property still will not work, for a different reason.}
The base version is now shared, so \code{\$(MafVersion)} covers the stable tier.
It breaks the moment you add a preview package, because the suffix carries a
build date --- \code{-preview.260730.1} --- that changes with every release and
is not derivable from the base version. Pin each prerelease package explicitly.

\textbf{A package \emph{off} the line is the signal.} This is the old ``a stale
train is a signal'' rule, sharpened: when everything ships together, a package
that did not ship is conspicuous. At the time of writing:

\begin{center}
\small
\begin{tabularx}{\linewidth}{@{}llX@{}}
\toprule
\textbf{Package} & \textbf{Stuck at} & \textbf{Reading} \\
\midrule
\pkg{Microsoft.Agents.AI.AzureAI} & 1.0.0-rc5 & Superseded by the
\code{Foundry} packages, which are its continuation \\[4pt]
\pkg{Microsoft.Agents.AI.FoundryMemory} & 1.0.0-preview & Four months
behind the line \\[4pt]
\pkg{Microsoft.Agents.AI.Mem0} & 1.0.0-preview & Nine months behind.
Treat as unmaintained until proven otherwise \\[4pt]
\pkg{Microsoft.Agents.AI.AGUI} & 1.13.0-preview & Three releases behind \\
\bottomrule
\end{tabularx}
\end{center}

\begin{note}
The merge is good news for anyone maintaining a solution: one number to track
instead of four, and a package's maturity readable from its suffix rather than
from cross-referencing dates. Do not carry forward the habit of assuming the
family is fragmented --- but do keep checking the suffix, because the version
number no longer distinguishes stable from alpha at all.
\end{note}

The sections that follow group packages by \emph{what they do}, not by maturity,
because maturity is now a per-package property you read off the version column.
Several groups mix tiers: the harness is stable while everything beside it is
preview, and GitHub Copilot is stable among prerelease providers. Where a table
shows \code{\mafcore{}-preview}, the version you actually pin carries a build
date as well --- \code{\mafpreview{}} at the time of writing.

Two further declarative packages sit on the same train and are omitted from the
table only because their names are too long for the column. Both extend the
declarative workflow runtime rather than replacing it:

\begin{itemize}[leftmargin=1.4em,nosep]
\item \pkg{Microsoft.Agents.AI.Workflows.Declarative.Foundry} --- the same
      format, targeting Foundry Agents.
\item \pkg{Microsoft.Agents.AI.Workflows.Declarative.Mcp} --- MCP server
      integration for declarative workflows. With the HTTP handler, this is the
      sandboxing seam described in \S\ref{sec:dur-declarative}.
\end{itemize}

\begin{note}
Note what is \emph{not} here: any Ollama, Bedrock or Gemini package. Those
providers are reached through the \pkg{Microsoft.Extensions.AI.*} connector
family instead (\S\ref{sec:supporting}), because the provider abstraction lives
below Agent Framework. See \S\ref{sec:seam} in Chapter~\ref{ch:first-agent}.
\end{note}

\begin{warning}
\index{namespaces!versus package names}
The namespace and the package name are not always the same word.
\code{using Microsoft.Agents.AI.Foundry.Hosting;} comes from the package of that
name --- but that package is on the preview tier, so adding it to a solution
otherwise pinned to stable versions means adding a version string with a build
date in it, not just the base number. This is the most common cause of a
confusing restore failure. See \S\ref{sec:trains}.
\end{warning}

\begin{warning}
\index{CodeAct!sandboxing}
\textbf{The two CodeAct packages have very different safety properties, and their
names do not tell you so.} The Hyperlight package executes generated code inside
a micro-VM. The local package does not sandbox at all --- it validates the
generated code's syntax tree, and its own description states that it requires
external sandboxing, such as a container or a VM.

Syntax-tree validation is not a security boundary. If you reach for the local
package because it has fewer moving parts, you have taken on the sandboxing
yourself, to the standard of \S\ref{sec:harness-shell}.
\end{warning}

\begin{note}
\pkg{Microsoft.Agents.AI.CosmosNoSql} is worth knowing about even if you never
use Cosmos DB, because it implements both storage abstractions the framework
expects you to supply. Chapter~\ref{ch:memory} implements the history side
against PostgreSQL by hand; Chapter~\ref{ch:workflows-advanced} uses the
checkpoint side.

The checkpoint abstraction is \api{ICheckpointStore<T>}, generic in the stored
representation. \api{JsonCheckpointStore} is an \emph{abstract base} rather than
a usable store, and \api{FileSystemJsonCheckpointStore} is the only concrete
in-box implementation. The manager is the sealed \api{CheckpointManager}, with
\code{CreateInMemory()}, \code{CreateJson(store, options?)} and \code{Default};
the manager interface and the in-memory manager are both internal and cannot be
named from your own code.
\end{note}

\section{Keeping this appendix current}

The list above will be wrong within a quarter. Rather than trusting it, generate
your own:

\begin{shellcmd}
# Every package published by the Agent Framework account, newest first
curl -s "https://azuresearch-usnc.nuget.org/query?q=owner:MicrosoftAgentFramework&take=100&prerelease=true" \
  | jq -r '.data[] | "\(.id)\t\(.version)"' | sort
\end{shellcmd}

Run it before each chapter you work through, and diff against
\code{Directory.Packages.props}. Two minutes of scripting removes an entire class
of wasted afternoon.

\begin{note}
If you intend to publish anything derived from this book, automate the check in
CI: a weekly job that restores against the latest available versions and reports
build failures tells you which chapters have rotted before a reader does.
\end{note}
